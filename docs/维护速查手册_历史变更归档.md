## 七、Mini 待机窗暗色化 + 团队之选一屏化（本轮）

### 7.1 Mini 待机窗（auxWindow）"白了吧唧"根因与修法

**根因**：`theme-system.css` 的 `:root` 默认就是亮色调色板（`--la-color-bg-primary: #f3f3f4`），主题属性没落到 `<html>` 上或选了亮色主题时整窗发白；且 BrowserWindow 原生底色默认为白。
**改动（2 文件，均为官方文件小改）**：

1. `src/main/shards/window-manager/aux-window/window.ts`：`browserWindowOptions` 里 `show: false,` 之后加一行
   `backgroundColor: '#141416', // [lolps] ...`（防白闪与透底）
2. `src/renderer/src-aux-window/NaiveUIProviderApp.vue`：三处主题取值全部钉死暗色——
   `getNaiveUiThemeOverrides('dark', true)`、`getNaiveUiTheme('dark')`、`useColorThemeAttr(() => 'dark', () => 'dark')`
   （`as` 仍用于 locale，不能删 import）
   **效果**：不管 App 主题设成什么，Mini 待机窗（大厅/排队/准备检查时弹的那个）永远黑底白字。
   **不想要这个窗**：主窗口 设置 → 小窗口（Mini Akari）可整个停用或关掉"自动弹出"，与本修改互不影响。

### 7.2 团队之选一屏自适应（不用往下滑）

**思路**：`DraftgapView.vue` 用 ResizeObserver 实时量 `.dgx-tbody` 可视高度，`fitCount = floor(高度/35)`，默认只渲染排序后前 fitCount 名（`displayed`），表格永远恰好一屏、零滚动条；**搜索框输入时显示全部匹配**（此时允许滚动）。工具条右侧有"一屏前 N 名 · 其余 M 个可搜索"提示。
**改动点**（全在自研文件，零冲突）：

- `DraftgapView.vue`：script 里 `filtered` 之后的 `[lolps] 一屏自适应` 代码块（ROW_PX/fitCount/tbodyEl/displayed/hiddenCount）；模板 `v-for` 用 `displayed`；`.dgx-tbody` 挂 `ref="tbodyEl"`
- 紧凑化：行高 44→34（改行高必须同步改 `ROW_PX = 行高+1`）、表头 34→26、头像 28→22、英雄名 15→13、胜率 17→15、选按钮 padding 4→2
- `TeamColumn.vue`：头部 padding 14→10、标题 26→22、大数字 34→30、卡片 min-height 84→64（600 高小窗也不溢出）
  **想多看几行**：把行高与 ROW_PX 再调小；想固定条数不自适应：把 `displayed` 里 `fitCount.value` 换成常数。

### 7.3 克制助手配色（无需再改）

`OpggCounterIntel.vue` 两列（打他胜率/单杀他概率）已是 `>0.5 绿 / 其余红`（即 >50% 绿、≤50% 红），随本包生效——之前看到全红是因为跑的还是旧构建。

## 八、赛后自动举报 · 全面检修（v2 强化版）

### 8.1 旧版为什么"不太能用"（两处根因）

1. **名单来源错了**：旧版从"点赞资格名单"（honor ballot 的 eligibleAllies/eligibleOpponents）取人。但这份名单是"**有资格被点赞**的人"——挂机、被系统标记的违规玩家恰恰会被剔除出去，也就是**最想举报的人反而不在名单里**；某些模式/情况下敌方名单还可能整个为空，导致"仅敌方"模式一个目标都没有。
2. **提交时机太早**：旧版在点赞投票界面一出现就立刻 POST 举报。客户端自己的举报按钮是在**结算数据页**（gameflow 进入 `EndOfGame`）才出现的，提前提交可能被 LCU 拒绝，而失败只写进日志，界面上毫无反馈，看起来就像"没反应"。

### 8.2 v2 的改法（report-controller.ts 全文重写）

- **名单**：改用 `GET /lol-end-of-game/v1/eog-stats-block` 拿**全员 10 人战绩名单**（含挂机者），自动识别敌我（isPlayerTeam / 按自己 puuid 判队），点赞名单降级为兜底；名单接口失败自动重试 3 次。
- **时机**：点赞界面只当"预热信号"，实际提交**等到进入结算数据页再执行**（最多等 120 秒，中途关开关会取消），再缓冲 2.5 秒。
- **重试**：每个目标最多提交 2 次；好友/房间名单各重试 2 次，仍失败则整局跳过（宁可不举报不误伤）并**在界面说明原因**。
- **可视化结果（新增）**：每局执行完，设置页"赛后自动举报"区块会出现"**上一局结果**"一行，例如"上一局：已举报 4 人（仅敌方）"或"好友列表获取失败，为避免误伤已跳过"。**以后好不好用一眼可见，不用翻日志。**
- 三重排除（自己/开黑/好友）、按 gameId 去重、跳过客户端已举报过的人：全部保留。

### 8.3 本次涉及文件

- 重写：`src/main/shards/auto-gameflow/report-controller.ts`
- 小改（各 1-2 处，均带 [lolps] 注释）：同目录 `state.ts`（+lastAutoReportSummary 字段与 setter）、`index.ts`（state propSync 列表 +1 键）、`src/renderer-shared/shards/auto-gameflow/store.ts`（+1 ref）、`src/renderer/src-main-window/views/automation/AutoGameflow.vue`（+"上一局结果"展示行，说明文案更新）

### 8.4 装上后怎么验收

打一局人机即可：结算数据页出现后几秒，去 自动化 → 赛后自动举报 看"上一局结果"行。

- 显示"已举报 N 人" → 通了。
- 显示"失败 N 人，详情见日志" → 把日志里 `Auto-report:` 开头的行发我，失败行会带 HTTP 状态码和响应体，照着改字段即可。
- 一直不出现"上一局结果"行 → 说明触发都没发生，把日志里有没有任何 `Auto-report:` 行告诉我。
  日志位置：主窗口 设置 → 应用 → 打开日志目录（或 `%APPDATA%/league-akari/logs`）。

## 九、对位构筑（整窗替换版：检测到对位后原界面数据直接变成对位版）

### 9.1 功能形态

选人确认对线对手后（自动判定 + 可在克制面板手动指定），OP.GG 窗口**原有界面**的
召唤师技能、符文配法、技能加点、初始装备、鞋子、核心装备、后续装备持有汇总等七个区块的数据**整体替换**为
「我的英雄 × 对位英雄」的专属数据——图标、排版、#1/#2、"应用"按钮全部原样，
只有数字变化（样本量会骤降到该对位的一两百场级，这是正常现象、也是验收标志）。
"应用"按钮与自动应用走官方原生管道（官方数据形状），符文置入随之恢复正常。
克制面板顶部新增一行"对位替换"小开关（默认开）与状态字
（"已切换完整对位构筑 vs XX（OP.GG · N 场 · 胜率 X% · 7/7 项）"）。英雄头部在对位生效时
只显示**该对位胜率 + 该对位总场次**，不再把通用登场率/禁用率混在旁边。

### 9.2 原理与涉及文件（v3：官方 target JSON 主链）

2026-08-30 实测确认，OP.GG champion JSON 已原生支持 `target_champion`。当前直接请求：
`/api/{region}/champions/ranked/{我的英雄}/{position}?tier=...&version=...&target_champion={对手id}`。
一次响应即含召唤师、`rune_pages`、完整符文、`skill_masteries`、加点顺序、前期装备与
`last_items` 后续装备持有汇总；
不再抓/解析 Next.js 网页 HTML。主进程把它转换为原版组件形状，渲染层用 Vue 的
"就近 provide 覆盖" merge 进当前英雄数据：

- `src/shared/http-api-axios-helper/opgg/index.ts` —— `targetChampion → target_champion`
- `src/main/shards/champion-data/matchup-build.ts` —— JSON 形状转换 + 样本真实性校验
- `src/main/shards/champion-data/counter-intel.ts` —— getMatchupBuild v3 + 缓存 + ipc
- `src/main/shards/champion-data/counter-intel-web.ts` —— 单杀率网页 URL 与当前补丁绑定
- `src/shared/types/counter-intel.ts` —— 完整地区/段位/版本请求与校验结果
- `src/renderer/src-opgg-window/opgg/matchup-overlay.ts` —— 覆盖数据、元信息和完整身份单例
- 改：`src/renderer/src-opgg-window/opgg/OpggView.vue` —— 就近 provide 覆盖 champion
  （merge 前再次核对全部筛选口径）
- 改：`src/renderer/src-opgg-window/opgg/OpggChampion.vue` —— 对位生效时显示对位胜率/场次

### 9.3 数据防线与真机排障

- **响应身份**：英雄 id 必须等于请求英雄；指定历史补丁时，响应 `meta.version` 必须完全一致；
  “最新”模式下 target 与通用基线也必须都返回版本且彼此相同，不能跨补丁比较。
- **目标样本实证（双响应）**：`target_champion` 响应没有回显目标 id，所以主进程会并行请求
  一份完全同地区/段位/分路/补丁、但不带 target 的通用基线。两份 `counters` 中该对手场次
  必须相差不超过 `max(5 场, 10%)`，否则视为不同统计快照并整次拒绝。每区只用最终能被
  原版组件解析的行计算样本母体 `N = Σplay / Σpick_rate`；target 区块要同时满足
  `Nt ≥ max(1, 0.25M)`、`Nt ≤ 2.5M + 10`、`Nt ≤ 0.5Ng`、
  `Ng - Nt ≥ max(10, 0.5M)`（M 为两份 counters 场次均值，Ng 为通用母体）。这会拒绝
  “target 被忽略、两份缓存仅相差 1–2 场”的伪差异；未通过的区块单独清空，至少两区通过
  才允许整份 overlay 生效。该规则刻意 fail closed：极端边界宁可显示通用版，也不冒充对位。
- **形状校验**：召唤师每行必须正好两个合法 id；完整符文必须主4/副2/碎片3；胜场不得
  大于场次；出门装的重复 id 原样保留（如两瓶药 `[1086,2003,2003]`）。第三方返回
  `null`、非数组或混合类型的技能/符文/装备时会逐行过滤，非法技能字符串不会进入原版组件。
- **缺项不混用**：七个 overlay 键及排位不应继承的 `prism_items` 全部显式写入，源里缺的
  区块写 `[]`，不会保留通用数据冒充对位数据。状态行显示 `7/7` 或“部分对位构筑”，
  展开后列出已替换/未替换。部分对位数据仍可诚实展示，但自动写客户端必须具备召唤师、
  符文、出门装、鞋、核心装、后续装备六个可写区块；缺任一项就整套回退当前通用构筑，
  不会拼成“半套对位 + 半套旧配置”。
- **失败不缓存**：只有通过校验的结果缓存 10 分钟；拒绝/空样本不缓存，可立即手动刷新重试。

排障：日志搜 `[MatchupBuild]`。成功行含 my/opp/position/region/tier/version/sections；
`拒绝未验证对位数据` 表示源响应没通过样本防污染，请把该行、窗口筛选和截图一起提供。

### 9.4 段位/区服/模式/版本口径

- **完整身份**：每份 overlay 强绑定
  `{我的英雄, 对手, 分路, region, tier, version, mode, source}`。基础视图与自动应用都逐项
  核对；原版位置筛选还会映射为 top/jungle/middle/bottom/utility 再与身份分路比较，
  `all/none` 也会拒绝覆盖。旧的 Global/All/Top 响应即使晚到，也不能合并进 KR/Emerald+/Mid。
- **写入名称与来源**：手动/自动生成的符文页与物品集名称都带 `vs 对手 · 来源`；来源按实际
  合并结果分成 `OP.GG`、`OP.GG+BZ`、`BZ` 三态。BZ 只筛符文或置顶既有真实行时也会标出，
  BZ-only 不会误写成 OP.GG；物品集 UID 同时含对手与来源，避免覆盖同英雄的通用方案。
- **段位与区服**：region 与 tier 直接进入 JSON 请求、缓存键与渲染身份；顶部筛选一变，
  旧 overlay 同步撤下并按新口径重取。
- **模式守卫**：仅"排位"模式做对位替换；ARAM / 大乱斗 / 无限火力 / 斗魂等模式
  自动停用（状态行显示"当前模式无对位数据"），绝不把排位对位数据错盖到其他模式上。
- **历史版本已支持**：version 显式传给 target JSON 并加入缓存键；实测 16.16 与 16.17

  “单杀他概率”的网页 URL 和各自缓存也全部绑定同一 version；源若回错补丁会直接拒绝。
- **对局锁定的新边界**：GameStart/InProgress/Reconnect 只锁“我方英雄/真实对手/分路”，

  修正请求成功前不会提前标记“已验证”。关开关会暂停真实阵容轮询，重开再恢复；结算/大厅
  才彻底清锁。原版顶部刷新与克制卡刷新都会绕过对位缓存同步重取。

### 10.15 对位构筑解析重写（历史方案；已由 10.19 的 target JSON 取代）

> 本节保留用于解释旧故障，不再是当前运行链路。当前版本不再抓 SSR/Flight；以后排障
> 不要继续调这里记载的网页锚点或正则，直接看 9.2、9.3 与 10.19。

- **现象**：船长 vs 阿卡丽，网页首选闪现+点燃（117 场 / 56.41%），我们却显示
  13 场 / 30.77% 的冷门；同页装备三段实测解析不出任何条目（悄悄回落通用数据）。
- **根因**：OP.GG 页面同时含 SSR HTML 表格与 React Flight 载荷。旧解析只吃 Flight：
  (1) "Summoner spells" 锚点在载荷里出现 6 次，旧代码取 lastIndexOf 恰好落在表格
  中段（跳过首行）；(2) Flight 行内数值被引用式压缩（"$51:props:..."），正则易错位；
  (3) 技能段未限定图标类型，装备图标会被当作技能 id 混入造出伪条目。
- **修复**：改以 **SSR HTML 表格为主解析面**（数值为明文 >56.41%< / >117 Games<，
  实测与网页逐项一致，行序即网页顺序），Flight 解析降级为兜底、仅补 HTML 未覆盖的
  区块；技能段严格只认 /spell/ 图标。4 项单测覆盖（含"拒绝装备图标混入"）。
  排障入口：matchup-build.ts 的 parseHtmlSections。
- **二次核验（三页真值逐项比对，全部吻合）**：劫 vs 塞拉斯（中/韩服/翡翠+）、
  船长 vs 阿卡丽（上/韩服/翡翠+）、盖伦 vs 诺手（上/全球/全段位，万场级样本）——
  召唤师技能 / 出门装 / 鞋 / 核心装四段的登场率、场次、胜率与网页逐项一致。
  过程中又抓到一条：React SSR 在文本节点间插注释（"332<!-- --> <!-- -->Games"），
  不剥离则装备三段的场次永远匹配不到（这正是装备段此前整体丢失的原因），
  现于解析前统一剥离注释。13 项单测锁定。**三轮复验又抓到两处**：
  (a) 辅助页的 "Support items"（日行车/天启对立）会被并进"鞋子"段——因为该区块未登记；
  (b) 页面同时渲染桌面/移动两套表格，同一条目重复。最终规则：区块标题取
  `<th ... align="left">`（列标题 Pick rate/Win rate 无 align，天然排除），
  **未登记标题自动成为边界、其行整段跳过**（未来新增区块不会再渗漏），
  条目按内容去重。复验覆盖：劫vs塞拉斯(中/韩/翡翠+)、船长vs阿卡丽(上/韩/翡翠+)、

### 10.23 复活自动切回游戏（2026-09-01 新功能）

- **是什么**：对局中死亡后，若人在其他窗口，**复活前 2 秒**自动把游戏窗口拉回前台。
  设置 → 杂项 → "复活自动切回游戏"（默认开；与"复活计时器"相邻，功能同源）。
- **安全边界（硬约束，改动时必须保持）**：数据来自 Riot 官方 Live Client Data API
  （本地 2999 端口，与原版复活计时器同一来源）；"是否在游戏里"问的是操作系统前台窗口；
  切回只做**操作系统层面的窗口激活**（等价 Alt+Tab）——`refocus-logic.ts` 生成的 PowerShell
  脚本只含 `AppActivate` 与 `SetForegroundWindow`，**不含任何按键/鼠标模拟**（单测明文断言
  不得出现 SendKeys/keybd_event/SendInput/mouse_event）。已知的"先按一下 Alt 解锁前台"手法
  属于输入模拟，**刻意不用**；Windows 拒绝后台抢前台时退化为任务栏闪烁。
- **状态机**（`RespawnRefocusTracker`，纯逻辑 13 项单测）：观测到死亡→武装；剩余≤2 秒触发
  一次并锁定；复活后解除武装、下次死亡重新武装；两次轮询之间直接复活（错过窗口）补触发
  一次；存活/开局/观战（找不到本人）永不触发。
- **轮询**：仅 `InProgress` 且开关开且 Windows 时运行；存活 1s 一查、死亡后 500ms（setTimeout
  链，不堆积）；加载期接口未就绪静默重试；Reconnect/结算/大厅/秒退/关开关一律停止并复位。
- **前台判断**：需要以管理员运行（原生 `isProcessForeground` 仅提权可用）；不可判断时保守地
  执行激活——对已在前台的窗口激活等价于无操作，所以"人本来就在游戏里"两种情况都无副作用。
- **防抖**：同一次死亡两次激活间隔≥5 秒；激活脚本 8 秒超时强杀；PowerShell 以
  `-EncodedCommand`（UTF-16LE Base64）传入，不受引号/换行影响；脚本内不得使用 `$pid`
  （PowerShell 保留变量）。
- **涉及文件**：新增 `src/main/shards/game-refocus/`（context/state/refocus-logic/
  game-refocus-controller/index + 测试）、`src/renderer-shared/shards/game-refocus/`
  （context/store/state-sync/index）；改 `src/main/bootstrap/index.ts`（+2 注册）、
  `src/renderer/src-main-window/shards/index.ts`（+2 注册）、`MiscSettings.vue`（+26 开关区块）。
  与官方待同步的两个提交零重叠。
- **可调区**：`context.ts` 的 `GAME_REFOCUS_LEAD_SECONDS`（提前秒数）、两档轮询间隔、
  5 秒最小激活间隔。
- **诚实边界**：独占全屏模式下 Windows 可能只允许任务栏闪烁而非切换（取决于系统前台锁策略）；
  首次真机实测若只闪烁不切，可考虑 `AttachThreadInput` 类不含输入模拟的增强手法。

### 10.24 冷门对位被误杀 + 对局内"未获取到你的分路"（2026-09-01 实测修复）

- **现象**：船长（上）vs 艾克，选人期与加载期都显示"对位数据获取失败：OP.GG 对位响应身份或
  样本校验未通过"；加载后分路栏显示"未获取到你的分路"；单杀率显示"数据源改版"。
- **根因一（真 bug，误杀冷门对位）**：OP.GG 的 `counters` 列表**只收前 60 个对手**。10.19 的
  防污染规则把"对手在 counters 里的场次"当作唯一锚点，锚点缺失即整份拒收——于是所有冷门对位
  （艾克上单、非主流分路等）全部被判"校验未通过"，尽管 target 数据明明是专属的
  （实测：各区母体约 13 场 vs 通用 16010 场）。
- **修法**：新增**无锚点验证**（`estimateUnanchoredMatchup`）：对手不在两份 counters 里时，
  改用"区块母体互证"——target 至少两个区块的母体彼此对齐（中位数 ±[0.25, 2.5x+10]）且相对
  通用母体缩小一半以上、绝对差≥max(10, 0.5M)。服务端若忽略 target，各区母体≈通用几千场，
  照样拒收（反例测试覆盖"忽略 target"与"缓存漂移 1195 vs 1200"）。最小样本 5 场。
  对位元信息（场次/胜率）由召唤师技能区块各行汇总得到（各行按技能组合划分整个母体）。
  有锚点的主流对位走原路径，行为不变。
- **根因二（显示误导）**：分路提示与下拉用的 `effectiveLane` 只读选人会话，选人结束即空；
  对位流水线其实走真实阵容推导（能拿到分路）。现新增 `inGameLane`（同 gameId 门），
  `effectiveLane` = 选人指派 → 对局内真实位置 → 手动。`IN_GAME_PHASES`/`LCU_TO_LANE`
  两个常量上提以规避 TDZ。
- **文案**：单杀率不可用改为"暂无单杀率数据（该对位样本不足或数据源异常）"，不再误报"改版"。
- **验证**：新增 `matchup-build-unanchored.test.ts` 5 项；既有 `matchup-build.test.ts` 18 项
  零回归（本地 vitest 垫片实跑）；实测船长 vs 艾克真实响应 7 区母体 [13,13,8,13,9,3,11]
  中位数 11，7/7 对齐且缩减，应通过。
- **诚实边界**：无锚点路径无法交叉验证"响应确属该对手"（有锚点时也只是校验两份快照一致，
  同样不回显对手 id），主要风险"target 被忽略"已由缩减规则覆盖。

### 10.25 Mini 窗回大厅黑屏自愈（2026-09-01 实测）

- **现象**：对局结束回大厅后 Mini 窗（aux window）整块黑屏，任务栏预览同为黑；正常应显示
  "单/双排积分·召唤峡谷 + 自动接受/自动匹配"面板。
- **判断**：主进程显隐时机与官方一致（对局期间 hide，回大厅 showOrRestore，官方原版同样如此），
  窗口位置尺寸正确（黑块恰为 426×525），渲染端 Indicator/Lounge 分支逻辑无误——问题在
  "显示后内容未绘制"。§7.1 当年看到的"白窗"极可能就是同一现象（BrowserWindow 默认白底），
  钉暗色只是把空白窗从白变黑。具体是渲染进程在游戏独占全屏期间崩溃/被回收（基类对
  `render-process-gone` 仅记日志不恢复）还是合成器未重绘，**离线无法区分**。
- **修法（与原因无关的自愈，`aux-window/window.ts`）**：show 后 `webContents.invalidate()` 强制
  重绘；800ms 后自检：`isCrashed()` 或页面 `innerText` 为空 → `reload()`。每次显示只自检一次，
  隐藏/销毁时取消；`onDispose` 清理。
- **验证方式**：真机打一局回大厅看 Mini 窗是否正常；若仍黑，应用日志会有
  "[lolps] aux window ... reloading" 记录，凭该记录可确认命中的是哪条分支。
- **v2（2026-09-02，5936f63 版仍复现后升级）**：第一版自检只看"渲染进程是否崩 / DOM 是否为空"，
  真机复现说明是"DOM 有内容但没画到屏幕"的合成器黑窗。升级为：① 从隐藏到显示时**无条件**做
  1px 尺寸往返（`_nudgeWindowSize`，60ms 回弹，无感）重建绘制表面；② 800ms 后
  `capturePage()` 按 8px 网格采样亮像素占比（暗色底 #141416 最大通道≈22，阈值 40），
  亮像素 <1% 判定为黑窗 → 再次尺寸微动 + `reload()`。日志会打印
  "aux window paint check: text=… bright=…%" 供定位。
- **v3（同日，依据日志 LA_20260902_165156712）**：日志显示这次回大厅（17:26:56 Lobby）后
  **完全没有 `BrowserWindow show` 记录**（同一会话此前四次回大厅均在 2ms 内有），也无崩溃/
  异常/visibility mismatch——即显示动作根本没执行到 `show()`。可能性只剩两种：时机判定
  未触发，或窗口被系统认作"已可见"（黑窗本体）。原版这条路径零日志，故 v3：
  ① reaction 每次判定打印 `aux timing=… phase=… autoShow=… ready=… nativeVisible=… stateShow=…`；
  ② `_hiddenByTiming` 标记：曾由时机逻辑隐藏、显示时系统却报可见 → 先 hide 再 show 强制重建；
  ③ showOrRestore 后仍不可见 → 直接 `show()`；④ 保留 v2 的尺寸微动与截屏自检。
  下一份日志凭 ① 的数值即可给出最终定论。
- **v4（最终定论，日志 LA_20260902_184420664）**：`aux show requested: fromHidden=true
nativeVisible=false minimized=true` ——窗口曾被**最小化**（Mini 窗标题栏有最小化钮 / 系统收起），
  随后选人期被我们 hide；回大厅时基类 `showOrRestore()` 见"已最小化"只 `restore()` 即返回，
  系统层面窗口可见（所以"仍不可见则强制 show"未触发），但 Chromium 未走真正 show 流程，
  内容停留隐藏态 → **窗口在、内容黑**。同日志中未最小化的那次回大厅走了 show，绘制自检
  bright=6.8% 正常，形成对照。修法：凡"从隐藏态回来"的显示由 aux 自行处理——最小化则先
  `restore()`，随后**一律真正 `show()`**，不再让基类提前返回；正常路径仍走 showOrRestore。
  v2/v3 的重绘、尺寸微动、截屏自检保留为防线。

### 10.26 Akari 评分（对局评分 · MVP / SVP / 尽力局，2026-09-02 新功能）

- **是什么**：战绩卡片折叠态在"补刀"列右侧新增"评分"列（本人分数 + 标签）；展开的总览表
  每个玩家位置标签旁显示各自分数；悬停任一分数弹出拆解（各项相对本局期望的倍数、分路、标签）。
- **算法（OP.GG OP Score 同类原则，全部离线，只读战绩摘要）**：
  ① 归一化：输出/承伤/推塔取**队伍份额**（÷1/5）；参团、视野/分、控制/分取**全局均值比**；
  经济/分、补刀/分优先与**同位置对手**均值比（无对手则全局均值）；死亡取份额反向
  （(1−份额)/(1−1/5)，0 死封顶）。单项比率上限 2.5。
  ② 分路加权：TOP/JUNGLE/MIDDLE/BOTTOM/UTILITY/UNKNOWN 六组权重（`AKARI_POSITION_WEIGHTS`，
  可调区，代码内自动归一）。位置缺失（LCU 摘要）时推断打野（野怪≥20 最多者）与辅助
  （补刀最少·视野最高），其余走 UNKNOWN。
  ③ 数据源未提供的项（整局全 0：视野/控制/推塔/承伤）自动剔除并重分配权重。
  ④ 映射：composite（1.0=平均）+ 单杀/多杀微加成（≤0.3）→ 5+5·tanh(2.5·(c−1))，四舍五入到 0.1。
  ⑤ 标签：MVP=全场最高；SVP=败方最高（与 MVP 重合时只记 MVP）；尽力局=输且 ≥8.0
  （`AKARI_CARRY_LOSS_THRESHOLD`）。仅两队模式计算（竞技场等返回空）。

### 10.31 对局评分：位置归一（2026-09-02，用户反馈"辅助分太高"实证修复）

- **根因**：参团/视野/控制/治疗护盾/伤害份额等指标原先与**全场 10 人均值**比，而这些量天然随位置
  偏斜（辅助参团 1.35×、视野 2.4×、控制 1.7×；AD 伤害份额 27% vs 辅助 12%）。实测一场十人平平无奇
  的局，两个辅助各 **16.6**（治疗 2.5×、视野 2.0×、控制 2.4×、参团 1.4×），其余 6.7–8.3——纯位置红利。
- **修法（`computeAkariMetrics`）**：每项指标的期望 = **同位置对手均值** 与 **位置基线期望** 各半
  （`AKARI_POSITION_BASELINES`：五位置在 dmg/tank/support/objective 份额与 kp/vision/cc 倍率上的典型值，
  可调区）；无同位置对手只用基线；位置未知退回全场口径。经济/补刀保持纯对线口径。
  纯"和对位比"曾试过：位置红利归零但矫枉过正（对手过菜即虚高，7/7/3 的劫被推到 11.1 尽力局；
  碾压者上限压缩），故取各半。
- **效果**：平平无奇一局十人 6.1–8.3（辅助 8.3，残差来自夹具与基线常量不一致）；真实对局：
  14/6/5 上单 12.8 MVP·Carry 局，劫 9.7 SVP，辅助 8.1/5.1，崩盘者 3.3/3.1。
- **下一步（未做）**：位置基线可在"校准"中按本人历史自动学习（每位置各原始比率均值），替换手工常量。

### 10.36 对局评分 vs OP.GG 对照校准（2026-09-03，4 局顶尖对局 40 人）

- **诊断（旧口径 ρ=0.53）**：① 输方被高估——份额按"占本队"计，输方总量小但份额照样合 100%
  （worker 5/9 上单 8.9 SVP vs OP.GG 3.4；MEECHOL 8.7 vs 3.4）；② 赢方辅助被低估（Bitter 2/4/22 参团 69%

  ④ 9/7/14 的 ADC 被判躺赢（队友被抬高后成队内最低）。

  改为 **占全场**（分母 = 全场总量 / 队数），打得少的队整体份额自然低，胜负效应来自真实表现而非加分；

### 10.38 中单研究 v2（2026-09-03）：游走判定从严 + 打野研究同款可视化

- **准确性交底**：Riot 时间线每 60 秒一帧坐标，只有击杀/建筑/野怪事件带精确坐标与时刻。因此
  首次游走时间精度 ±1 分钟，一分钟内往返的短游走可能漏计——这是数据源上限，无法"确保"。
- **旧算法问题**：任何离开中路带的坐标都算游走，河道插眼 / 帮野 / 打龙被计成"入侵"方向。
- **v2 算法**（`analyzeOneTimelineV2`）：
  游走 = 身处**严格边路走廊**（上：x<3000∧y>5000 或 y>12000∧x<11000；下：y<3000∧x>4000 或 x>12000∧y<10500，
  龙坑/男爵坑/河道草均排除）的分钟帧，连续同走廊帧合并为一段；走廊内本人参与的击杀不在任何段 ±60s 内则单独成段；
  成功 = 段 ±90s 内有本人参与击杀。另算：2–14 分钟位置点与击杀参与点（热力图，官方 `classifyMapZone` 三分区）、
  分区权重、10:00 帧相对敌方中单的补刀差/经济差/领先率（`MidLiteGame.enemyMidPid` 由 teamPosition=MIDDLE 取得）、
  单杀（无助攻主杀）、被单杀（仅中路带内，排除游走被反与被抓）、14 分钟前参团率。
- **界面**：`PlayerInfoCardMidlaneResearch.vue` 改为打野研究同款——触发行：48px 热力图 + "N 场 · 游走型/对线型/均衡（偏上/偏下）"
  - 分区权重 上/中/下 + 10 分钟经济差；悬停面板：140px 地图（位置点+击杀参与点）+ 地图偏好/游走（游走率、场均次数、
    首次游走中位、成功率、去向）/对线（补刀差、经济差、领先率、首杀等级、单杀、被单杀）/前期参团 四个区块 + 算法说明与精度提示。
    复用官方 `GankMap`、`JunglePathingSection`。数据加载/缓存/取消逻辑不变。
- 测试：`midlane-research-v2.test.ts` 4 项（走廊判定、片段合并与成功、10 分钟对线差、被单杀口径），旧测试零回归。
